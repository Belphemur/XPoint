# Design: GT911 touch controller — sleep toward touch-only wake

**Date:** 2026-09-24
**Status:** Proposed (no implementation started)
**Scope:** X4 Pro (GT911) first; X4C (GPIO6 SD / GT911 too) rides along; C3 boards without GT911 unaffected.
**Sources:**
- GT911 datasheet Rev.09 (2015-03-11), Goodix — fortec-integrated.de copy, verified in-tree at no tool requirement (text layer extracted).
- Firmware: `freeink-sdk/libs/hardware/InputManager/src/InputManager.cpp`, `freeink-sdk/libs/hardware/PowerManager/src/PowerManager.cpp`, `crosspoint-x-reader/lib/hal/HalPowerManager.{h,cpp}`, `crosspoint-x-reader/src/main.cpp`.
- Companion analysis: `docs/design/stock-firmware-power-architecture.md`, `references/standby-idle-drain.md` (skill crosspoint-battery-drain).

## 1. Problem

During awake-idle (reading pause, home screen, before the 10-min auto-sleep) the GT911 is
ranked suspect #1 on the idle-drain list: it is the only X4 Pro peripheral that does real
periodic analog scanning while the CPU sits in `delay(10)` slices.

Firmware facts (file:line):
- Powered rail: `touch.powerEnable = GPIO2`, **active-low** (LOW = powered). Driven LOW at
  boot by OEM parity; held LOW through idle; cut only by `powerDownRailsForSleep()`
  (`PowerManager.cpp:113`) at deep sleep.
- Host-side cost: `InputManager::pollGt911()` (`InputManager.cpp:2383-2527`) polls status
  reg `0x814E` over I2C every loop iteration; throttled to `GT911_LOW_POWER_POLL_MS` only
  when `setLowPowerPolling(true)` (SDK PR #2) — an active-mode improvement, not a sleep.
- INT (GPIO10) is used only as a level during the address-select dance
  (`resetWithIntLevel()`, `InputManager.cpp:2092-2101`). There is **no** interrupt
  callback on INT; all touch detection is host-polled.

## 2. What the GT911 itself can do (datasheet, Rev.09 §8.1, §10.4)

Operating modes and measured currents (DC table, ambient 25 °C, AVDD 2.8 V):

| Mode | Entry | Scan behavior | Current (typ/max) | Wake |
|---|---|---|---|---|
| Normal | default | ≥ 7–10 ms refresh cycle, INT pulses per scan while touched | **8 mA / 14.5 mA** | — |
| Green | automatic after no-touch 0–15 s (config `one step = 1s`) | 40 ms scan cycle | **3.3 mA** | automatic on touch |
| Doze | config | auto-reduced reporting | **0.78 mA** | automatic |
| Sleep | host I2C command; **requires host to drive INT low before the command** | no scanning | **70–120 µA** | host drives INT **high 2–5 ms** → Normal mode |
| Gesture | host sends command `8` to `0x8046`, then to `0x8040` | gesture scan only | *(not specified)* | INT pulse > 250 µs on swipe / double-tap / letter |

Timing facts:
- Sleep entry window: interval between screen-off (sleep) command and any sleep-exit/wake
  attempt must be **> 58 ms** (§8.1 d).
- Response deadline: Sleep mode wake response **< 200 ms**; Green mode **< 48 ms**;
  full init **< 200 ms** (§2 Features).
- INT triggering is configurable (rising vs falling edge, §8.2). While—it is touched it
  emits a pulse every scanning cycle.
- I2C host bus "always initiated by the host"; GT911 is slave-only. In Sleep mode it does
  not ACK until woken: **the host must not poll while asleep**.
- Gesture wake requires the external diode-to-INT circuit of the sample schematic
  (§5 schematic note: "To enable gesture wake-up, this circuit should be connected to
  INT pin"). **Hardware presence on X4 Pro unverified — see risks.**

## 3. Design: a tiered idle policy (progressive, never impaired)

Trigger: the existing `IDLE_POWER_SAVING_MS`-driven low-power state (80 MHz + poll
throttle) — extended with a time-since-last-input inactivity hierarchy, not a new timer
source beyond the existing idle window (same design principle as the deep-sleep sink:
fix at the real sink, driven by existing triggers).

### Tier A — align poll cadence with Green mode (no register writes)

Green mode is **automatic** (no-touch 0–15 s, configuration-dependent). Once it engages
the device only produces new frames every ~40 ms. The current 100 ms low-power poll is
already slower than that — no change needed, but add a `LOG_DBG` counter of
no-new-frame polls to *confirm on hardware* that Green mode actually engages on this
module (the module's config may pin refresh farther down).

Gain expectation: small (avoids a few pointless I2C polls), but mainly it *measures*
what mode the controller is in — the baseline that decides whether Tiers B/C pay for
themselves.

### Tier B — enter GT911 Sleep mode at sustained idle; wake-on-demand

- **Entry** (≈3–5 min after last touch, coinciding with the SD/GPI rides — see idle
  park umbrella): drive INT (GPIO10) low, wait a tick, then write the sleep command to
  the command register (Goodix reference-driver convention: command byte at `0x8040`,
  sleep = `0x05`; exact value must be validated against the module — the register map
  section was deleted from Rev.07+ of the datasheet, so the value is NOT
  datasheet-source. Mark this a **must-verify-on-hardware** step).
- **Wake**: host drives INT high for 2–5 ms (`gpio_hold`-pattern, corner case: `release
  hold` before reconfig to OUTPUT is not needed here — the pin is ESP-driven, no pad
  holds on GPIO10 today), then resumes polling `0x814E`. Response < 200 ms; budget one
  poll cycle of latency in `mappedInputManager` bookkeeping before any touch is acted
  on. First read after wake that returns a polled-down frame must be ignored (it is a
  stale latch), same as the existing transient-failure handling
  (`InputManager.cpp:2398-2405`).
- **Result**: 3.3 mA → 0.07–0.12 mA while asleep, with zero UI-latency change while
  touching. The **entry/exit latency is bounded and only touched in the idle window**,
  not between page turns — the constraint that killed the SD-between-pages idea does
  not apply here: wake cost is ≤ ~230 ms once, when the user comes back, and the SoC
  only *learns* touch via polling so there is no interrupt path to lose.
- USB caveat: while a serial monitor is attached (HWCDC), skip entry — debugging
  sessions must not fight sleep transitions in the log.
- Sleep-mode blocking of the touch-capacitive **home key** must be honored: the home
  key is also reported by the GT911 (status bit 0x10). While asleep, tapping the capaci-
  tive home key is invisible. Mitigate: **physical side buttons remain host-polled and
  fully functional while asleep** (they are separate GPIOs), and the auto-sleep window
  (10 min) is far beyond the Tier-B entry delay.

### Tier C — rail cut at long idle (pre-auto-sleep only)

Drive GPIO2 HIGH (active-low rail OFF) via the same `holdRailOff` idiom
(`PowerManager.cpp:83-90`) when idle approaches the auto-sleep timeout, and re-init on
any touch INT change or button press. This is effectively "GT911 power-down" — mode
selection does not matter because the part is depowered. Cost: touch re-init is the
full power-on dance (address-select via INT level, `resetWithIntLevel`, ~200 ms init),
latency ~250 ms once at return. Do **not** combine with Tier B entry in the same idle
window: pick per unit whether B suffices — C makes B meaningless while the rail is cut.

Not proposed: leaving GPIO2 gated during active reading. The panel's held rail already
biases other consumers; GT911 cost during active use is the *scanning*, not VDD, and
scanning is what the sleep mode itself eliminates.

## 4. What needs hardware verification (ranked)

1. **Does the module honor the sleep command?** Write sleep command, measure GPIO2 rail
   current across the X4 Pro (or use the existing sleep-trace MA arithmetic with GT911
   actively vs. sleep-parked on a series ammeter).
2. **Gesture-mode silicon variant**: sample schematic requires the diode-to-INT gesture
   circuit. Gesture mode is the only way to get *touch-triggered wake* with the host
   also asleep. Until the X4 Pro board file proves that diode, **do not plan on
   gesture wake** — and do not write gesture-mode config into any PR.
3. **Does Green mode auto-engage** on the X4 Pro's OEM-inherited config (§8.1a: the
   auto-switch timer must be configured in the config block)?
4. **Sleep command exact opcode** for this firmware family (`0x8040` value) and whether
   it collides with the home-key status bit state machine.

## 5. Estimate of gain (1100 mAh cell)

- Current awake-idle GT911 cost: between **3.3 mA** (Green auto) and **8 mA**
  (Normal with no auto-Green gap, plus host-polling overhead).
- Tier A: zero savings; provides data.
- Tier B (Sleep at idle): **−3.2 mA to −7.9 mA** during idle-awake windows.
- Tier C (rail-off at deep idle): same as B while engaged, plus removes the rail's
  own overhead; gain is bounded by actual idle minutes.
- Daily effect depends on reading-pause share, not page-turn share — same class as the
  SD park estimate (~0.1–2 mA→0.02), but roughly **3–10× the SD card's magnitude**,
  which is why GT911 sits at the top of the idle-drain suspect list.

## 6. Verification plan for the implementation PR

1. `pio run -e x4pro` then `-e default` (C3 compatibility floor — no GT911 on C3,
   all entry points must be `#if`-gated or no-op when `gt911Addr == 0`).
2. On hardware: serial trace over `scripts/debugging_monitor.py` showing
   - enter: `LOG_INF("TOUCH", "GT911 sleep entered after %lu ms idle")`
   - exit on button/touch: `LOG_INF("TOUCH", "GT911 wake, resuming poll")`
   - no `TouchActivity` events recorded while asleep.
3. Battery sanity: `sleep_trace.csv` mA across an idle-awake window pre/post park.
4. UI: tap mid-page exactly at the 5-min boundary; a page turn must land without any
   visible latency beyond the ≤230 ms first-poll budget.
